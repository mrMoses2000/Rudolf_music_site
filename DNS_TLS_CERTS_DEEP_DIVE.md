Документ отвечает на вопросы:
- что именно мы поменяли у провайдера в DNS;
- как устроены DNS‑серверы и что реально происходит при резолве;

Везде ниже речь про домен `musikschule-cms-bielefeld.de` и его `www`.

---

## 0) Что мы меняли у провайдера (конкретно)

### 0.1 A‑записи
Мы сделали так, чтобы **DNS возвращал IP нашего сервера**:
- `@` (apex, корневой домен) → `3.79.24.73`
- `www` → `3.79.24.73`

Это означает: при обращении к домену и `www` клиент получает IP и подключается к серверу напрямую.

### 0.2 Почему это важно
DNS **не содержит порт** (исключение — SRV, браузеры для HTTP его не используют). Порт выбирается протоколом:
- `http://` → порт 80
- `https://` → порт 443

Поэтому нам было критично, чтобы домен резолвился **в правильный IP**, а HTTP/HTTPS уже решается на уровне сервера.

### 0.3 Отключение URL‑перенаправления (Weiterleitung)
Перенаправление — это **HTTP‑редирект, выполняемый провайдером**, а не DNS.
Если оно включено, провайдер может отдавать 301/302 до того, как запрос дойдёт до вашего сервера.
Для certbot это плохо (особенно HTTP‑01), поэтому перенаправление отключили и оставили чистый DNS.

## 1) DNS: от имени до IP

### 1.1 Кто участвует
1) **Stub resolver** на вашей машине (libc / systemd‑resolved).
2) **Recursive resolver** (обычно DNS провайдера или 1.1.1.1/8.8.8.8).
3) **Root DNS** (13 логических корней).
4) **TLD‑серверы** (`.de`).
5) **Authoritative DNS** (сервер, где лежит зона `musikschule-cms-bielefeld.de`).

### 1.2 Итеративный и рекурсивный поиск
- **Итеративный**: клиент сам идёт root → TLD → authoritative.
- **Рекурсивный**: клиент просит resolver сделать всё и вернуть ответ.

Обычно клиент делает рекурсивный запрос своему resolver.

### 1.3 Кэш и TTL
Каждая запись имеет TTL (в секундах). Resolver кэширует и отвечает из кэша, пока TTL не истёк.
Это объясняет «задержки» при смене DNS: кэш может быть старым.

### 1.4 Какие записи реально нужны для сайта
- **A** — IPv4 для домена/хоста.
- **AAAA** — IPv6 (если есть).
- **CNAME** — алиас (обычно `www` → `@`, но мы поставили `A` напрямую).
- **NS** — на какие DNS‑серверы делегирован домен.
- **SOA** — служебные данные зоны.
- **CAA** — какие CA имеют право выпускать сертификаты.

### 1.5 Почему DNS не знает порта
DNS фиксирует **имя → IP**. Порт — это часть транспортного/прикладного протокола.
Есть SRV записи, где задаются порты, но **браузеры их игнорируют** для HTTP/HTTPS.

### 1.6 Математическая модель DNS (как отображение)
Пусть `Σ` — алфавит допустимых символов доменных имён.  
Тогда домен — строка `d ∈ Σ*`.\n\nDNS можно мыслить как отображение:\n```\nF: Σ* → P(RR)\n```\nгде `RR` — множество ресурсных записей, а `P(RR)` — множество всех подмножеств.  
То есть DNS возвращает **набор записей**, а не одно значение.\n\nДалее мы выбираем нужный тип:\n```\nA(d) = { r ∈ F(d) | type(r)=A }\n```\n\nЭто важно: DNS — не «таблица имя→IP», а **функция имя→набор данных**.\n+

## 2) Как устроено DNS‑сообщение (по байтам)

DNS‑пакет (UDP или TCP) содержит:
- Header (ID, flags, счётчики секций)
- Question (имя, тип записи, класс)
- Answer
- Authority
- Additional

DNS работает обычно по **UDP/53**. Если ответ большой — переключается на **TCP/53**.

Дополнительно:
- **EDNS0** расширяет размер пакета и добавляет опции.
- **DNSSEC** добавляет подписи и ключи (RRSIG, DNSKEY), чтобы гарантировать целостность зоны.

## 3) DNS в ОС (Ubuntu)

### 3.1 Путь `getaddrinfo()`
Приложение (например, certbot или браузер) вызывает:
```
getaddrinfo("musikschule-cms-bielefeld.de")
```
Далее:
- смотрится `/etc/nsswitch.conf`
- проверяется `/etc/hosts`
- идёт запрос через `systemd-resolved` или напрямую по `/etc/resolv.conf`

### 3.2 systemd‑resolved
- слушает `127.0.0.53:53`
- кэширует ответы
- решает, в какой upstream resolver идти

### 3.3 Где это видно
- `resolvectl status` — состояние резолвера
- `dig`/`nslookup` — вручную проверить ответы

## 4) Где рождаются сертификаты (процесс CA)

### 4.1 Базовые сущности
- **Сервер** создаёт **пару ключей**: `(sk, pk)`.
- **CSR** (Certificate Signing Request) содержит `pk`, домены и подпись `sk`.
- **CA** (Certificate Authority) проверяет владение доменом и подписывает CSR.

### 4.2 Откуда берутся CA
- Root CA (встроены в доверенное хранилище ОС/браузеров).
- Intermediate CA — подписаны root‑ом, выпускают реальные сертификаты.

### 4.3 Цепочка (chain)
Сервер отправляет клиенту:
- свой сертификат
- промежуточный сертификат(ы)

Клиент проверяет цепочку до корневого сертификата (который заранее доверен).

---

## 5) Как DNS участвует в получении сертификата

CA должна убедиться, что заявитель **контролирует домен** (Domain Control Validation). Это делается через ACME‑челленджи.

### 5.1 HTTP‑01
- CA делает DNS‑резолв домена → получает IP.
- CA подключается по HTTP (порт 80) к `http://<domain>/.well-known/acme-challenge/...`.
- certbot отвечает этим токеном.

**Зависимость от DNS:** если DNS не указывает на ваш сервер, CA не увидит challenge.

### 5.2 DNS‑01
- CA запрашивает TXT‑запись `_acme-challenge.<domain>`.
- Вы должны поставить TXT в authoritative DNS.
- CA проверяет наличие значения и выпускает сертификат.

**Зависимость от DNS:** CA напрямую спрашивает authoritative сервер.

### 5.3 TLS‑ALPN‑01
- CA подключается на порт 443 и ожидает специфический TLS‑ответ.

### 5.4 CAA
CAA‑запись может запретить выпуск сертификатов «не тем» CA.
Если CAA ограничивает, Let’s Encrypt не сможет выпускать.

## 6) Математика под капотом (без «магии»)

### 6.1 Хэш‑функция
Функция `H(m)`:
- детерминирована
- сложно восстановить `m` по `H(m)`
- маленькие изменения дают другой результат

### 6.2 Подпись сертификата
CA делает:
```
sig = Sign(sk_CA, H(tbsCertificate))
```
Клиент проверяет:
```
Verify(pk_CA, H(tbsCertificate), sig) == true
```
Это **математическое доказательство**, что сертификат выдал именно CA.

### 6.3 ECDHE (обмен секретом)
- Выбирается эллиптическая кривая над конечным полем.
- Есть операция «сложение точек» (алгебра на конечном множестве).
- Секреты `a` и `b` дают:
```
A = a*G
B = b*G
S = a*B = b*A
```
Наблюдатель видит `A` и `B`, но не может восстановить `S`.

### 6.4 HKDF и симметричные ключи
Из общего секрета выводятся ключи для шифрования, MAC и т.д.

### 6.5 RSA и ECDSA (очень короткая формализация)
**RSA (идея):**\n+- выбираем простые `p, q`, `n = p*q`\n+- `φ(n) = (p-1)(q-1)`\n+- выбираем `e`, затем `d` так, что `e*d ≡ 1 (mod φ(n))`\n+- подпись: `sig = H(m)^d mod n`\n+- проверка: `H(m) ?= sig^e mod n`\n\n**ECDSA (идея):**\n+- над эллиптической кривой выбирается секрет `d`\n+- публичный ключ `Q = d*G`\n+- подпись вычисляется через модульную арифметику в поле\n\nЕсли нужно, распишу формулы полностью с примером на малых числах.\n+

## 7) Что делает ОС во время выпуска сертификата

### 7.1 certbot и HTTP‑01
1) certbot создаёт временный сервер и слушает порт 80.
2) CA делает DNS‑резолв домена.
3) CA подключается к IP → получает challenge.
4) certbot закрывает сервер и записывает сертификаты в `/etc/letsencrypt/...`.

### 7.2 Где проходят пакеты
1) Пакет приходит на NIC → DMA в память.
2) Драйвер создаёт `sk_buff`.
3) netfilter → DNAT (если Docker) → сокет процесса certbot/nginx.
4) Процесс читает из сокета → отправляет ответ.

### 7.3 Как формируется пакет (структуры на уровне сети)
**Ethernet frame:**\n+- MAC‑адреса источника/назначения\n+- EtherType (IPv4/IPv6)\n+\n**IP‑пакет:**\n+- src/dst IP\n+- TTL, протокол (TCP/UDP)\n+\n**TCP‑сегмент:**\n+- src/dst port\n+- sequence/ack\n+- flags (SYN/ACK)\n+\n**TLS record:**\n+- тип записи\n+- длина\n+- зашифрованные данные\n+\nИменно так «байты» превращаются в реальную сетевую доставку.\n+

## 8) Типичные причины поломок

1) DNS не обновился (TTL, кэш).
2) A‑запись указывает не на тот IP.
3) Порт 80/443 закрыт в firewall/SG.
4) CAA блокирует Let’s Encrypt.
5) На 80/443 слушает не тот процесс.
6) Время на сервере сильно отличается (TLS чувствителен ко времени).

```
Изменили A запись
  → DNS resolver возвращает новый IP
    → CA может достучаться до сервера (HTTP‑01)
      → certbot получает challenge
        → CA подписывает сертификат
          → браузер доверяет цепочке
            → HTTPS работает
```
