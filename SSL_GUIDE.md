# SSL_GUIDE.md — Математика TLS/HTTPS и сертификатов (учебное пособие)

Цель: дать формально точное, математически обоснованное и практическое объяснение TLS/HTTPS, сертификатов и цепочек доверия. Фокус — причинно‑следственные связи и минимальная «магия». Всё, что не является строгой необходимостью, помечено как «контекст».

---

## 0) Базовая модель: кто кому что доказывает

**Задача TLS:**
1) **Аутентифицировать** сервер (убедиться, что мы говорим с нужным доменом).
2) **Создать общий секрет** (ключ), который известен только клиенту и серверу.
3) **Защитить трафик** (конфиденциальность + целостность).

**Следствие:**
- Сертификат доказывает **связь домена и публичного ключа**.
- Шифрование трафика выполняется **симметричным ключом**, который получается в ходе TLS.
- Сертификат **не** шифрует трафик — он «привязывает» ключ к домену.

## 1) Математическая база (минимум, который нужен)

### 1.0 Минимум теории групп (короткое введение)

Раз ты знаком с множествами и векторными пространствами, вот мостик:

**Группа** — это множество `G` с одной операцией `⊙`, для которой выполняются 4 свойства:
1) **Замкнутость:** `a ⊙ b ∈ G`
2) **Ассоциативность:** `(a ⊙ b) ⊙ c = a ⊙ (b ⊙ c)`
3) **Нейтральный элемент:** существует `e`, где `a ⊙ e = e ⊙ a = a`
4) **Обратимость:** для каждого `a` существует `a⁻¹`, где `a ⊙ a⁻¹ = e`

Если ещё выполняется **коммутативность**, группа называется **абелевой**.

**Векторное пространство** — это по сути *абелева группа по сложению* плюс операция умножения на скаляр.  
Поэтому ниже, когда говорится «группа», можно мыслить «множество с операцией», которая ведёт себя строго по этим 4 правилам.

### 1.1 Модулярная арифметика
Все операции выполняются в конечных множествах (полях и группах).

- Поле: \(\mathbb{F}_p\), где \(p\) — простое.
- Операции: \(+, -, \times, \div\) мод \(p\).

### 1.2 Группы и дискретный логарифм
В TLS 1.3 используется **Diffie‑Hellman** на эллиптических кривых:

- Есть группа \(G\) и генератор \(g\).
- Клиент берёт секрет \(a\), вычисляет \(A = g^a\).
- Сервер берёт секрет \(b\), вычисляет \(B = g^b\).
- Общий секрет: \(S = B^a = A^b = g^{ab}\).

**Причина безопасности:** задача дискретного логарифмирования сложна — из \(A\) невозможно получить \(a\) за разумное время.

### 1.3 Хэш‑функции
Используются криптографические хэши (SHA‑256/384):

- \(H(x)\) — фиксированный размер вывода.
- Свойства: коллизии очень сложны, предобраз сложен.

### 1.4 Подписи (RSA/ECDSA/EdDSA)
Цель: доказать владение приватным ключом.

**Общая схема:**
- Подпись: \(\sigma = \text{Sign}(sk, H(m))\)
- Проверка: \(\text{Verify}(pk, H(m), \sigma) = \text{true}\)

## 2) Сертификат X.509 (как структура и как доказательство)

Сертификат — бинарная структура ASN.1 (DER). PEM — лишь Base64‑обёртка.

Упрощённо:
```
Certificate ::= SEQUENCE {
  tbsCertificate       TBSCertificate,
  signatureAlgorithm   AlgorithmIdentifier,
  signatureValue       BIT STRING
}
```

**TBSCertificate** (то, что подписывается) включает:
- version
- serialNumber
- issuer
- validity (notBefore/notAfter)
- subject (обычно домен)
- subjectPublicKeyInfo (публичный ключ сервера)
- extensions (SAN, keyUsage, EKU, SKI/AKI, AIA и т.п.)

**Ключевой факт:**
Подписывается **tbsCertificate**, а не весь сертификат.

### 2.1 Подпись сертификата математически
Пусть CA имеет:
- приватный ключ \(sk_{CA}\)
- публичный ключ \(pk_{CA}\)

CA вычисляет:
\[
\sigma = Sign(sk_{CA}, H(tbsCertificate))
\]

Клиент проверяет:
\[
Verify(pk_{CA}, H(tbsCertificate), \sigma) = true
\]

**Следствие:** если подпись валидна, данные сертификата не подделаны, и публичный ключ действительно «одобрен» CA.

## 3) Цепочка доверия

Сертификат сервера сам по себе **не доверен**. Доверие строится цепочкой:

```
Leaf (сервер) -> Intermediate CA -> Root CA (доверенный)
```

### 3.1 Алгоритм проверки цепочки
1) Взять leaf.
2) Проверить подпись leaf ключом intermediate.
3) Проверить подпись intermediate ключом root.
4) Root уже находится в trust store браузера/ОС.

### 3.2 Почему это нужно
- Root‑ключи хранятся в браузерах/ОС.
- Intermediate позволяют масштабировать выпуск без риска компрометации root.

## 4) TLS 1.3 — строго по шагам

### 4.1 Обозначения
- Клиент: C
- Сервер: S
- ECDHE общие параметры: группа \(G\)
- Хэш: \(H\)

### 4.2 Сообщения
1) **ClientHello**: версии, шифры, SNI, ECDHE key_share \(A\)
2) **ServerHello**: выбранный шифр, key_share \(B\)
3) **EncryptedExtensions**
4) **Certificate** (цепочка)
5) **CertificateVerify** (подпись транскрипта)
6) **Finished** (MAC транскрипта)
7) **Finished** (со стороны клиента)

### 4.3 Вывод ключей
1) \(S = A^b = B^a\)
2) Key schedule (HKDF):
   - handshake_secret
   - client/server handshake traffic secrets
   - client/server application traffic secrets

### 4.4 AEAD‑шифрование
Каждая запись TLS шифруется AEAD:

\[
C, tag = AEAD\_Encrypt(K, nonce, plaintext, AAD)
\]

- **K** — ключ сессии
- **nonce** — на основе sequence number
- **AAD** — заголовок TLS записи

**Следствие:** данные защищены от изменения и подслушивания.

## 5) Как клиент убеждается, что сервер настоящий

Причинно‑следственная цепочка:
1) Сервер прислал сертификат → публичный ключ сервера.
2) Клиент проверяет подпись сертификата по цепочке.
3) Клиент проверяет домен в SAN.
4) Сервер подписывает handshake транскрипт приватным ключом (CertificateVerify).
5) Клиент проверяет подпись публичным ключом из сертификата.

Если все проверки проходят → сервер действительно владеет приватным ключом.

---

## 6) Почему сертификат не шифрует трафик

Сертификат = публичный ключ + подпись. Публичный ключ сам по себе **не секрет**.
Шифрование делается **симметрично**, потому что:
- симметричные алгоритмы быстры;
- ключи можно безопасно согласовать через ECDHE.

## 7) ACME / certbot (математически это не меняет TLS)

ACME — это **протокол доказательства владения доменом**. Он не влияет на математику TLS, только на то, **как появляется сертификат**.

HTTP‑01:
- Сертификат выдаётся только после доказательства, что вы контролируете домен.

## 8) Cloudflare как TLS‑прокси (математически)

Cloudflare создаёт **две** TLS‑сессии:

```
Клиент <—TLS1.3—> Cloudflare <—TLS1.3—> Origin (ваш сервер)
```

**Следствие:**
- Клиент проверяет сертификат Cloudflare.
- Cloudflare проверяет сертификат вашего сервера (в режиме Full strict).
- Это два независимых рукопожатия, два набора ключей, два набора шифротекстов.

## 9) Мини‑справочник терминов
- **SAN** — список доменов в сертификате.
- **EKU** — для чего допустим сертификат (serverAuth и т.п.).
- **HKDF** — ключевая схема на основе HMAC.
- **AEAD** — алгоритмы, совмещающие шифрование и проверку целостности.

## 10) Что проверять, если «не работает»
- Домен в SAN?
- Срок действия не истёк?
- Цепочка валидна?
- Подпись CertificateVerify проходит?
