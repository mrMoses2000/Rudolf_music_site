# TLS/HTTPS и сертификаты "под капотом"

Этот файл — техническое, но практичное объяснение: что такое сертификат (как набор байтов), какие операции реально выполняются, кто их выполняет и в какой последовательности, и какую роль начинает играть Cloudflare как промежуточный TLS‑узел.

---

## 1) Что такое сертификат (как набор байтов)

Сертификат — это **X.509 структура в ASN.1 DER**, то есть строго определённая бинарная (байтовая) структура.

PEM‑файл — это просто **Base64‑кодированный DER** с заголовками:

```
-----BEGIN CERTIFICATE-----
...base64...
-----END CERTIFICATE-----
```

Внутри DER структура выглядит (упрощённо) так:

```
Certificate ::= SEQUENCE {
  tbsCertificate       TBSCertificate,
  signatureAlgorithm   AlgorithmIdentifier,
  signatureValue       BIT STRING
}
```

**TBSCertificate** (то, что подписывают) содержит:
- version
- serialNumber
- signature (алгоритм подписи)
- issuer (кто выдал)
- validity (notBefore / notAfter)
- subject (кому выдан)
- subjectPublicKeyInfo (публичный ключ сервера)
- extensions (SAN, keyUsage, EKU, AIA, AKI/SKI, etc.)

**signatureValue** — это подпись CA над байтами `tbsCertificate`.

Итого: сертификат — это **публичный ключ + метаданные + подпись CA**.  
Секретного там **нет**, всё публично.

---

## 2) Что такое цепочка сертификатов

Один сертификат не живёт сам по себе. Обычно сервер отдаёт **цепочку**:

```
[leaf (ваш домен)] -> [intermediate CA] -> [root CA]
```

Клиент **не доверяет leaf**, он доверяет **root** (корень), потому что root уже есть в системном хранилище доверенных корневых сертификатов ОС/браузера.

Проверка цепочки:
1) Клиент берёт leaf, проверяет подпись leaf публичным ключом intermediate.
2) Проверяет подпись intermediate публичным ключом root.
3) Root уже trusted (в trust store).

---

## 3) Как проверяется сертификат (операции и порядок)

На стороне клиента (браузера) делается **строгая последовательность проверок**:

1) **Парсинг** ASN.1 DER → извлекаются поля.
2) **Верификация подписи** leaf:
   - Берётся `tbsCertificate` (bytes),
   - Берётся `signatureValue`,
   - Берётся публичный ключ CA (из intermediate),
   - Выполняется криптографическая проверка подписи.
3) **Проверка срока** (notBefore/notAfter).
4) **Проверка имени**: домен в SAN (Subject Alternative Name).
5) **Проверка ключевых ограничений** (Key Usage / Extended Key Usage).
6) **Проверка цепочки до trusted root**.
7) (Опционально) **OCSP/CRL**: проверка отзыва.

Важно: если хоть один шаг не проходит — TLS рукопожатие рвётся.

## 4) TLS 1.3 — что происходит на проводе (байты и вычисления)

### 4.1 Этапы на уровне сообщений

**Клиент → Сервер:**
1) `ClientHello`
   - версии TLS
   - набор шифров
   - SNI (имя домена)
   - поддержка ALPN (например, h2)
   - ECDHE key share (публичная часть эфемерного ключа)

**Сервер → Клиент:**
2) `ServerHello`
   - выбранный шифр
   - свой ECDHE key share
3) `EncryptedExtensions`
4) `Certificate` (цепочка)
5) `CertificateVerify` (подпись handshake‑транскрипта приватным ключом сервера)
6) `Finished` (MAC от handshake‑транскрипта)

**Клиент → Сервер:**
7) `Finished`

После этого идёт защищённый `Application Data`.

### 4.2 Что вычисляется

Ключевые вычисления в TLS 1.3:

1) Клиент и сервер делают ECDHE:
   - `shared_secret = ECDH(client_priv, server_pub)`
2) Далее HKDF (key schedule):
   - handshake_secret
   - client/server handshake traffic secrets
   - client/server application traffic secrets
3) Для каждого направления (client → server, server → client) создаются ключи AEAD (AES‑GCM или ChaCha20‑Poly1305).
4) Каждая запись TLS имеет **счётчик/sequence number**, из которого строится nonce.

### 4.3 Что доказывает, что сервер владеет приватным ключом

`CertificateVerify` — сервер подписывает хэш транскрипта handshake **своим приватным ключом**.  
Клиент проверяет подпись публичным ключом из сертификата.

Если сервер **не владеет приватным ключом**, подпись не сойдётся → handshake ломается.

## 5) Что происходит в ОС (Ubuntu) и в процессах

### 5.1 TCP/TLS (HTTP/2)

1) **NIC** принимает Ethernet‑фреймы → ядро.
2) **IP слой** собирает пакеты → проверяет заголовки.
3) **TCP** собирает сегменты в поток байтов.
4) **Socket** передаёт байтовый поток в процесс (nginx).
5) **OpenSSL (userland)** читает поток:
   - парсит TLS записи,
   - расшифровывает,
   - проверяет MAC/AEAD,
   - отдаёт HTTP слой.

### 5.2 QUIC/TLS (HTTP/3)

1) Приходит UDP‑пакет.
2) Ядро отдаёт его в userland (QUIC стек).
3) TLS 1.3 встроен прямо в QUIC (не отдельные записи TLS поверх TCP).
4) QUIC сам управляет потерями/ретрансмитами.

HTTP/3 = TLS 1.3 внутри QUIC (UDP), меньше задержки на потере пакетов и быстрее старт.

## 6) Как выпускается сертификат (Let’s Encrypt + certbot)

Схема ACME (HTTP‑01):
1) `certbot` создаёт запрос и сообщает CA: "я владею доменом".
2) CA просит доказательство: "положи токен по URL".
3) certbot поднимает временный сервер на 80 порту, отвечает токеном.
4) CA делает HTTP‑запрос к домену → получает токен.
5) CA выпускает сертификат, подписывает своим ключом.

В итоге у вас:
```
fullchain.pem = leaf + intermediate
privkey.pem   = ваш приватный ключ
```

## 7) Где здесь Cloudflare и как он использует сертификаты

После включения Cloudflare:

```
Клиент ─TLS─> Cloudflare ─TLS─> ваш сервер
```

### 7.1 Клиент ↔ Cloudflare
- Cloudflare отдаёт **свой сертификат** для вашего домена.
- Клиент проверяет цепочку до доверенного корня.
- Внешний клиент **никогда не видит ваш Let’s Encrypt сертификат**.

### 7.2 Cloudflare ↔ ваш сервер (origin)
- Cloudflare подключается к вашему серверу по HTTPS.
- Здесь он **проверяет ваш сертификат** (если режим Full (strict)).
- Ваш Let’s Encrypt остаётся важным, иначе strict не пройдёт.

### 7.3 Кеширование
Если картинка есть в кеше Cloudflare:
- Запрос **не идёт** на ваш сервер,
- TLS с вашим сервером **не используется**,
- Ответ отдаётся прямо с edge.

## 8) Причинно‑следственная связь «пакет → TLS → контент»

### Без Cloudflare
1) DNS → IP вашего VPS.
2) TCP handshake.
3) TLS handshake (сертификат сервера).
4) HTTP запрос.
5) Ответ → браузер.

### С Cloudflare
1) DNS → IP Cloudflare.
2) Клиент делает TLS handshake с Cloudflare.
3) Cloudflare либо отдаёт кеш, либо:
4) Cloudflare делает TLS handshake к вашему VPS.
5) Забирает HTML/картинки.
6) Отдаёт клиенту.

### Почему становится быстрее
1) TLS/HTTP‑3 на edge ближе географически.
2) Кеш экономит RTT до вашего сервера.
3) Браузер получает ответы быстрее, даже если ваш сервер медленнее.

## 9) Что будет, если что‑то сломается

Типовые симптомы:
- **ERR_SSL_VERSION_OR_CIPHER_MISMATCH** → старый TLS/неправильная конфигурация origin.
- **525/526 (Cloudflare)** → Cloudflare не может установить TLS к origin (сертификат/strict).
- **526** → invalid cert на origin.
- **522** → origin не отвечает.

Проверки:
1) `curl -Iv https://musikschule-cms-bielefeld.de` → какой сертификат отдаётся.
2) `curl -Iv https://3.79.24.73` → работает ли origin напрямую.

## 10) Короткий итог

Сертификат — это публичный ключ + метаданные + подпись CA (байты ASN.1/DER).  
TLS — это протокол, который:
1) проверяет сертификат,
2) договаривается об эфемерных ключах,
3) шифрует все дальнейшие данные.

Cloudflare добавляет **второй TLS‑уровень** между клиентом и вашим сервером, даёт кеш и быстрый edge, поэтому первый заход становится быстрее.
