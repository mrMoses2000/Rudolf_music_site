Формат: как у преподавателя. Я сам задаю вопросы, которые обычно возникают, и отвечаю так, чтобы не было «провалов» в цепочке.

## 0) Карта процесса «URL → пиксели»

```
URL
  → Политики/кэш/Service Worker
    → DNS
      → TCP/QUIC
        → TLS
          → HTTP
            → HTML → DOM
              → CSS → CSSOM
                → Style → Layout → Paint → Composite → GPU
```

Это не линейный конвейер: браузер делает всё **параллельно**, а рендер идёт **инкрементально**.

## 1) Архитектура браузера (процессы и изоляция)

**Вопрос:** браузер — это один процесс?  
**Ответ:** нет. Типичная схема (Chromium‑подобные):

- **Browser process** — UI, вкладки, политика безопасности, навигации.
- **Renderer process** — выполняет HTML/CSS/JS и рисует страницу.
- **GPU process** — композитинг и рендер слоёв.
- **Network process** — DNS, TCP/TLS, HTTP.
- **Utility processes** — декодеры, PDF, WebAssembly и т.п.

**Вопрос:** зачем это?  
**Ответ:**
- **Безопасность:** рендер в песочнице.
- **Надёжность:** краш вкладки не валит браузер.
- **Производительность:** GPU и сеть вынесены отдельно.

### 1.1 IPC и песочница
Процессы общаются через IPC (в Chromium — Mojo).  
Renderer не имеет прямого доступа к файловой системе или сети — запросы идут через browser/network process.

## 2) Ввод адреса и подготовка навигации

**Вопрос:** что происходит после Enter?  
**Ответ:**

1) **Парсинг URL**
   - нормализация домена (Punycode для IDN), декодирование.
   - если схема не указана → пробуем https.

2) **HSTS**
   - если домен в HSTS, https обязателен.

3) **Service Worker**
   - может перехватить навигацию и отдать ответ из Cache Storage.

4) **HTTP Cache**
   - проверка памяти/диска на валидный ответ.

5) **Preconnect / DNS Prefetch**
   - браузер может заранее открыть DNS/соединение.

## 3) DNS и сетевое подключение

**Вопрос:** кто делает DNS?  
**Ответ:** обычно системный резолвер, но браузер держит собственный кэш и prefetch.

Порядок:
- `getaddrinfo()` → системный resolver
- resolver обращается к рекурсивному DNS
- ответ A/AAAA

**Важный факт:** DNS даёт **IP**, но **не порт**.

### 3.1 TCP/QUIC
- TCP: SYN → SYN‑ACK → ACK.
- QUIC (HTTP/3): поверх UDP, быстрее на повторных соединениях.

### 3.2 TLS
- ClientHello (SNI, ALPN, cipher suites)
- ServerHello + сертификат
- проверка цепочки
- ECDHE → ключи
- Finished

## 4) HTTP и кэширование

### 4.1 Запрос
- метод, путь, заголовки.
- cookies отправляются автоматически, если домен подходит.

### 4.2 Ответ
- статус, заголовки, тело.

### 4.3 Кэш
- `Cache-Control: max-age`
- `ETag` + `If-None-Match`
- `Last-Modified` + `If-Modified-Since`

**304** означает: «бери из кэша».

### 4.4 Пулы соединений
Браузер переиспользует TCP/TLS соединения для одного origin, чтобы не делать handshake заново.

### 4.5 MIME и декодирование
Браузер проверяет `Content-Type`, декодирует `gzip/br` и решает, как интерпретировать поток байтов.

## 5) HTML → DOM (подробно)

1) **Tokenization**: поток байтов превращается в токены.
2) **Tree construction**: строится DOM дерево.
3) Встроенные `<script>` могут **остановить парсер**.

### 5.1 Почему скрипт блокирует парсер
Потому что JS может изменить DOM до продолжения. Чтобы DOM был согласован — парсер ждёт.

### 5.2 async/defer/module
- `defer` — скрипт грузится параллельно, выполняется после парсинга.\n+- `async` — скрипт выполняется сразу после загрузки (может прервать парсер).\n+- `type=\"module\"` — поддерживает импорт, выполняется как defer.\n+

## 6) CSS → CSSOM

- CSS парсер строит CSSOM.
- DOM + CSSOM → Render Tree.

### 6.1 Каскад и специфичность
Решает, какое правило победит.

### 6.2 Preload scanner и приоритеты
Отдельный сканер HTML ищет `<link rel=\"preload\">`, `<img>`, `<script>` и ставит их в очередь загрузки с приоритетами.

## 7) Style, Layout, Paint, Composite

### 7.1 Style
Вычисление конечных стилей для всех узлов.

### 7.2 Layout
Расчёт размеров/позиции. Изменения `width`, `font-size`, `display` приводят к reflow.

### 7.3 Paint
Рисование в слои.

### 7.4 Composite
GPU собирает слои и выводит кадр.

**Почему `transform` быстрее?** Он работает на уровне compositing, без layout/paint.

### 7.5 Потоки внутри renderer
- **Main thread**: DOM, layout, JS.
- **Compositor thread**: скролл и анимации.
- **Raster threads**: растеризация слоёв.

## 8) JavaScript: движок и исполнение

### 8.1 Внутренности JS‑движка
1) Парсинг → AST.
2) AST → bytecode.
3) Интерпретатор выполняет bytecode.
4) JIT компилирует горячие участки.

### 8.2 Оптимизации
- hidden classes
- inline caches
- speculative optimization

### 8.3 GC
- generational GC
- mark‑and‑sweep
- stop‑the‑world паузы возможны

## 9) Event loop

Очереди:
- **Task queue** (setTimeout, network)
- **Microtask queue** (Promise.then)

Цикл:
1) выполнить одну task
2) выполнить все microtasks
3) render

---

## 10) JS ↔ DOM: причина «forced reflow»

Если JS читает `offsetWidth` сразу после DOM‑изменений, браузер вынужден срочно пересчитать layout.
Это вызывает просадки FPS.
