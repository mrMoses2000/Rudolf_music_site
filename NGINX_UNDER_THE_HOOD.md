# NGINX_UNDER_THE_HOOD.md — зачем нужен nginx и как он работает (подробно)

Цель: дать преподавательское объяснение, зачем появился nginx, какую проблему решает и как устроен «под капотом».

---

## 1) История и мотивация

**Проблема C10k:** в начале 2000‑х веб‑сервера упирались в пределы при ~10k одновременных соединений.
Традиционная модель (процесс/поток на соединение) приводила к:
- росту памяти
- большому числу context switch
- «простоям» CPU при блокирующем I/O

**nginx** появился как **событийный, неблокирующий сервер**, способный обслуживать тысячи соединений с минимальными накладными расходами.

---

## 2) Архитектура процессов

### 2.1 Master process
- читает конфигурацию
- открывает порты
- запускает workers
- перезапускает их при сбоях

### 2.2 Worker processes
- слушают сокеты
- принимают соединения
- обрабатывают HTTP
- работают в event loop

**Важно:** workers — это **несколько процессов**, а не потоки. Это повышает стабильность.

---

## 3) Модель ввода‑вывода (event‑driven)

nginx использует неблокирующие сокеты + `epoll`:

1) `epoll_wait()` сообщает о готовности сокета.
2) Worker читает данные, обрабатывает, пишет ответ.

**Ключевая идея:** один worker может обслуживать тысячи соединений, потому что не блокируется на медленных клиентах.

---

## 4) Как nginx обрабатывает запрос

### 4.1 Фазы обработки
У nginx есть «фазы» (phase handlers):
- чтение запроса
- переписывание (rewrite)
- доступ (access)
- контент (content)
- логирование

### 4.2 Локации
nginx выбирает `location` по правилам:
- точное совпадение
- префикс
- regex

После выбора локации применяются директивы (`root`, `try_files`, `proxy_pass`).

---

## 5) Отдача статических файлов

Оптимизации:
- **sendfile** — zero‑copy из page cache в сокет.
- **open_file_cache** — кеширует file descriptors и stat.
- **AIO** — асинхронное чтение диска (опционально).

Эти механизмы делают nginx быстрым для статического контента.

---

## 6) Reverse proxy

nginx может проксировать запросы:
- балансировка нагрузки
- кеширование
- заголовки безопасности

Для SPA это полезно, если появится backend.

---

## 7) TLS в nginx

nginx использует OpenSSL:

1) Клиент подключается → TLS handshake.
2) nginx читает `fullchain.pem` и `privkey.pem`.
3) OpenSSL проверяет и устанавливает сессию.
4) HTTP идёт по защищённому каналу.

**Сессии:** TLS session resumption ускоряет повторные подключения.

---

## 8) HTTP/2 и HTTP/3

- HTTP/2: мультиплексирование запросов поверх одного TCP.
- HTTP/3: поверх QUIC/UDP, чаще через CDN.

---

## 9) Почему nginx нужен в этом проекте

- терминирует TLS
- отдает статические файлы быстрее, чем Node
- задаёт кэш‑заголовки
- позволяет позже подключить backend
