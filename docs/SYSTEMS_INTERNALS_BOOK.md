# Введение: Veth vs Bridge (Разъяснение)

Прежде чем мы погрузимся в недра, давайте проясним ваш последний вопрос: **"Veth — это и есть мост, или нет?"**.

Нет, это **две разные структуры** `net_device`, связанные отношениями "Master — Slave".

### 1. Аналогия "Железа"
*   **Bridge (`docker0`)**: Это **свитч** (коммутатор). У него есть *таблица MAC-адресов* (Forwarding Database). Сам по себе он "виртуальный", но ведет себя как умная коробка с портами.
*   **Veth Pair**: Это **патч-корд** (кабель). У него два конца.
    *   Один конец (`eth0` внутри контейнера) втыкается в сетевую карту "компьютера" (контейнера).
    *   Второй конец (`vethXXXX` на хосте) втыкается в порт свитча (`docker0`).

### 2. Структуры в ядре (C-Level)
Когда вы запускаете докер, в памяти ядра существуют **два независимых объекта** `struct net_device`:

1.  **Объект А (`name="docker0"`, `type=bridge`)**
    *   Это голова. У него есть спискок портов.
    *   `priv_flags |= IFF_EBRIDGE`.

2.  **Объект Б (`name="veth7f1a"`, `type=veth`)**
    *   Это просто интерфейс-труба.
    *   **Критический момент (Подключение):** Когда Docker делает `ip link set veth7f1a master docker0`, в структуре Объекта Б меняется поле:
        ```c
        veth_dev->master = bridge_dev; // Указывает на Объект А
        ```
    *   И регистрируется перехватчик:
        ```c
        veth_dev->rx_handler = br_handle_frame;
        ```

### 3. Как это работает вместе
Пакет вылетает из контейнера -> летит по трубе -> вылетает из `veth7f1a`.
Драйвер `veth` хочет отдать пакет в стек хоста. Но ядро видит `rx_handler`.
Ядро говорит: "Ага, этот интерфейс подключен к мосту". И передает управление **функции моста**.
Мост (`Obj A`) берет пакет, смотрит на его MAC-адрес и решает, куда кинуть (в другой порт или себе в стек).

**Итог:** `veth` — это провод. `bridge` — это устройство управления, к которому подключен провод. У провода есть указатель на мастера (`bridge`).

# PART I: Архитектура и Топология

## 1. Общая архитектура

```
[ Пользователь ] <---> [ Интернет ] <---> [ NIC (eth0) ]
                                            |
                                       (Ядро Linux: Netfilter/NAT)
                                            |
                                       [ Docker Bridge (docker0) ]
                                            |
                                       [ veth Interface ]
                                            |
                                       [ Container Namespace ]
                                            |
                                       [ Nginx Process ]
```

### Компоненты
1.  **Host OS (Ubuntu):** Базовая система. Управляет "железом", файрволом и Docker Daemon.
2.  **Docker Daemon:** Контроллер namespaces и cgroups. Настраивает `iptables` для NAT.
3.  **Container (`music_school_app`):** Изолированное пространство имен (PID, MNT, NET).
4.  **Nginx:** Процесс внутри контейнера (PID 1), слушающий порты 80 и 443 **внутри контейнера**.

## 2. Путь входящего пакета (Детально)

Пользователь (IP `1.2.3.4`) отправляет HTTPS запрос (`TCP SYN` на `3.79.24.73:443`).

### 2.1 Host Ingress
1.  **Физический уровень:** Пакет приходит на `eth0`.
2.  **Netfilter (PREROUTING):** Docker DNAT.
    *   Ядро видит правило: "Все, что на хост:443, переписать DstIP на `172.17.0.2:443`".
    *   IP назначения меняется с публичного на приватный.
3.  **Routing Decision:** Ядро видит, что `172.17.0.2` доступен через `docker0`.

### 2.2 Bridge и Veth
1.  Пакет уходит в `docker0`.
2.  Мост (`docker0`) по ARP-таблице знает, что IP `172.17.0.2` принадлежит MAC-адресу, который висит на порту `vethXXXX`.
3.  Пакет отправляется в `vethXXXX`.
4.  Моментально выпадает из `eth0` внутри контейнера.

# PART II: Рождение сети (Lifecycle)

## 1. Рождение интерфейсов (Syscalls & Netlink)

В Linux интерфейсы создаются через **Netlink** — IPC канал.

### 1.1 Как Docker создает сеть
1.  **Bridge (`docker0`):** `netlink_send(RTM_NEWLINK, type="bridge")`. Ядро вызывает `alloc_netdev`.
2.  **Veth Pair:** `RTM_NEWLINK` тип `veth`. Ядро создает пару `vethHost` <-> `vethPeer`.
3.  **Namespace Isolation:**
    *   Docker делает `clone(CLONE_NEWNET)` для создания контейнера.
    *   Шлет команду `ip link set vethPeer netns <PID>`.
    *   Ядро переносит `vethPeer` в список девайсов нового процесса. С этого момента `eth0` существует только в мире контейнера.

## 2. Как клиент понимает, куда слать? (Routing Decision)

### Сценарий: Клиент хочет на ваш сервер
Клиент знает только публичный IP.
1.  **DNAT:** Магия происходит на входе в хост. Клиент не знает про ваши виртуальные интерфейсы.
2.  Ядро хоста подменяет IP назначения.
3.  Далее работает обычный роутинг: "Ага, этот IP в той локальной сети, шлю пакет туда".

# PART III: Kernel Deep Dive (C Level)

## 1. Структура `struct net_device` и Namespace

```c
struct net_device {
    char                    name[IFNAMSIZ]; 
    struct net              *nd_net; // <--- ГЛАВНОЕ: Указатель на Namespace
    const struct net_device_ops *netdev_ops; // VTable драйвера
    rx_handler_func_t       *rx_handler; // <--- Перехватчик моста
    struct net_device       *master;     // <--- Ссылка на мост
    // ...
};
```

### Телепортация интерфейса
Когда интерфейс переносится в контейнер (`dev_change_net_namespace`), ядро просто меняет указатель `dev->nd_net`.
Все функции поиска (`dev_get_by_name`) фильтруют устройства по этому указателю. Поэтому хост "слепнет" и перестает видеть `eth0`, который ушел в контейнер.

## 2. Forwarding Path (`ip_forward`)

Путь пакета `sk_buff` при форвардинге:

1.  **`ip_rcv`**: Валидация заголовков.
2.  **`NF_HOOK(PRE_ROUTING)`**: Срабатывает DNAT. `daddr` меняется.
3.  **`ip_route_input`**: Решение маршрутизации.
    *   Результат: `dst_entry` с функцией `input = ip_forward`.
4.  **`ip_forward`**:
    *   Уменьшение TTL (`--ttl`).
    *   Пересчет контрольной суммы.
    *   `NF_HOOK(FORWARD)`.
5.  **`ip_output`**: Отправка в исходящий интерфейс.

# PART IV: Bridge Internals

Как именно работает захват управления?

### 1. Регистрация `rx_handler`
Команда `ip link set dev master bridge` делает:
```c
dev->rx_handler = br_handle_frame;
dev->master = bridge;
```

### 2. Перехват пакета
В функции приема `__netif_receive_skb_core`:
```c
if (skb->dev->rx_handler) {
    return skb->dev->rx_handler(&skb); // Вызов br_handle_frame
}
```
Вместо того чтобы пакет пошел в IP стек (`ip_rcv`), он уходит в логику моста.

### 3. Логика моста (`br_handle_frame`)
1.  Смотрит MAC назначения.
2.  Ищет в FDB (Forwarding Database): "На каком порту этот MAC?".
3.  Если нашел -> `br_forward` (меняет `skb->dev` на целевой порт).
4.  Если пакет для самого моста -> `br_pass_frame_up` (отдает в IP стек хоста).

# PART V: Network Stack (Kernel to User)

Путь от "провода" до `read()` в Nginx.

1.  **NIC & DMA:** Карта пишет байты в Ring Buffer в RAM.
2.  **NAPI & IRQ:** SoftIRQ вызывает `poll()`, драйвер создает `sk_buff`.
3.  **IP Stack:** Проходит проверки (см. выше).
4.  **TCP Stack:**
    *   Проверка Sequence/ACK.
    *   Данные копируются в Receive Queue сокета.
    *   Сокет помечается "Readable".
5.  **Epoll:** Nginx просыпается (`epoll_wait` возвращает `EPOLLIN`).
6.  **`read()` Syscall:**
    *   Переключение контекста User/Kernel.
    *   `copy_to_user()`: Ядро копирует данные из `sk_buff` (Kernel) в буфер Nginx (User).

# PART VI: Cryptography Math (TLS 1.3)

Что происходит внутри OpenSSL после `read()`.

### 1. Симметричная (AES-GCM)
*   Данные шифруются потоковым шифром (AES CTR).
*   Аутентификация (MAC) через полиномы в поле Галуа **GF(2^128)** (GHASH).
    *   Сложение: XOR.
    *   Умножение: Полиномиальное по модулю `x^128 + x^7 + x^2 + x + 1`.

### 2. Асимметричная (Handshake)
*   **ECDHE (Обмен ключами):**
    *   Группа точек эллиптической кривой `y^2 = x^3 + ax + b`.
    *   Операция сложения точек (геометрически: хорда и касательная).
    *   Сложность дискретного логарифма: зная `G` и `k*G`, найти `k` невозможно.
*   **RSA (Подпись):**
    *   Кольцо вычетов `Z_n`.
    *   Теорема Эйлера: `m^φ(n) ≡ 1`.
    *   Подпись — это возведение хеша в степень секретного ключа `d`.
