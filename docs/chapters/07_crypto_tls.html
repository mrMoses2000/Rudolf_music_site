Глава 7: Криптография и TLS 1.3

Самая математически насыщенная часть. Как передать секрет по открытому каналу?

7.1. Elliptic Curve Diffie-Hellman (ECDH)

В TLS 1.3 мы используем кривую Curve25519. Ее уравнение:

$$y^2 = x^3 + 486662x^2 + x \pmod {2^{255}-19}$$

ВЫВОД: ОБЩИЙ СЕКРЕТ (SHARED SECRET)

Пусть $G$ — базовая точка кривой (генератор).

  1. Client: Генерирует секретное число $a$ (private key).
    Вычисляет публичный ключ $A = a \times G$. (Умножение точки на скаляр).
    Отправляет $A$ серверу в сообщении ClientHello.
  2. Server: Генерирует секретное число $b$.
    Вычисляет $B = b \times G$.
    Отправляет $B$ клиенту в ServerHello.
  3. Magic:
    Клиент вычисляет $S = a \times B = a \times (b \times G)$.
    Сервер вычисляет $S = b \times A = b \times (a \times G)$.

Поскольку умножение на скаляр коммутативно ($a \cdot b = b \cdot a$), они получают одинаковую точку $S$. Координата $x$ этой точки становится общим секретным ключом (Pre-Master Secret).

7.2. Арифметика в полях Галуа (AES-GCM)

Шифрование — это не проблема. Проблема — это аутентификация (убедиться, что данные не подменили). Для этого используется GCM (Galois Counter Mode), работающий в поле Галуа $GF(2^{128})$.

Полином поля: $$P(x) = x^{128} + x^7 + x^2 + x + 1$$

Операция умножения в этом поле ($A \otimes B$) сложна для обычного CPU. Поэтому Intel добавил инструкцию PCLMULQDQ (Carry-less Multiplication), которая выполняет полиномиальное умножение аппаратно. Это позволяет шифровать и подписывать трафик на скоростях 10-100 Гбит/с.

7.3. Сертификаты X.509 и Цепочка Доверия

Как браузер узнает, что ключ $B$, присланный сервером, действительно принадлежит rudolf-music.ru, а не хакеру посередине? Ответ: Цифровая Подпись.

НУКЛЕОЛЯРНЫЙ УРОВЕНЬ: СТРУКТУРА ASN.1

Сертификат — это структура Certificate, описанная на языке ASN.1. 

    Certificate  ::=  SEQUENCE  {
        tbsCertificate       TBSCertificate,  -- "To Be Signed" (Body)
        signatureAlgorithm   AlgorithmIdentifier,
        signatureValue       BIT STRING       -- The Encrypted Hash
    }
    
    TBSCertificate  ::=  SEQUENCE  {
        version         [0]  EXPLICIT Version DEFAULT v1,
        serialNumber         CertificateSerialNumber,
        signature            AlgorithmIdentifier,
        issuer               Name,            -- Who signed this? (R3)
        validity             Validity,        -- NotBefore / NotAfter
        subject              Name,            -- Who owns this? (rudolf-music.ru)
        subjectPublicKeyInfo SubjectPublicKeyInfo, -- THE PUBLIC KEY ITSELF
        extensions      [3]  EXPLICIT Extensions OPTIONAL
    }

Самое важное поле — subjectPublicKeyInfo. Именно тут лежит публичный ключ сервера ($e, n$ для RSA или точка $P$ для ECC), который мы используем для обмена ключами.

МАТЕМАТИЧЕСКОЕ ДОКАЗАТЕЛЬСТВО: КОНКРЕТНЫЙ ПРИМЕР

Перестанем говорить абстракциями. Давайте "взломаем" RSA на калькуляторе. Представим, что мы — CA (Certificate Authority), и подписываем хеш сертификата.

1. Генерация ключей CA (Keygen)
Взяли два простых числа: $p = 61, q = 53$.
Модуль $n = p \times q = 3233$.
Функция Эйлера $\phi(n) = (61-1)(53-1) = 3120$.
Выбрали открытую экспоненту $e = 17$ (должна быть взаимно проста с $\phi(n)$).
Вычислили секретную экспоненту $d = 2753$ (обратное к $e$ по модулю $\phi(n)$).
Public Key: $(17, 3233)$, Secret Key: $(2753, 3233)$.
2. Подписание (Signing)
Пусть хеш сертификата $H = 65$. (В реальности это 32 байта SHA-256).
CA вычисляет подпись $S$, используя свой SECRET KEY $d$:
$$S = H^d \pmod n = 65^{2753} \pmod{3233} = 2790$$
Число 2790 записывается в поле signatureValue сертификата.
3. Верификация (Verification)
Браузер получает сертификат, видит подпись $S = 2790$.
Браузер знает PUBLIC KEY CA ($e=17, n=3233$) — он зашит в ОС.
Браузер вычисляет:
$$H_{check} = S^e \pmod n = 2790^{17} \pmod{3233}$$
Если посчитать (через Modular Exponentiation), результат будет 65.
$$65 == 65$$
Магия работает. Никто, не зная $d=2753$, не мог бы подобрать такое число $S=2790$, которое при возведении в 17-ю степень даст 65.
