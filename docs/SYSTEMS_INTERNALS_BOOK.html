Hardware & DMA

Сетевая карта (NIC) — это автономный компьютер. Она не ждет приказов CPU на каждый байт. Вместо этого они используют общую "почтовую ячейку" в оперативной памяти — Ring Buffer.

1.1. Молекулярный Уровень: Запись в Память

Что происходит на уровне транзисторов и шины, когда пакет прилетает в карту?

CAUSAL CHAIN: DIRECT MEMORY ACCESS (DMA)

  1. Fetch: NIC считывает свой внутренний регистр RDT (Tail Index). Пусть он равен 5.
  2. Address Calculation: NIC вычисляет физический адрес дескриптора в RAM: $$Addr = Base + (5 \times 16)$$
  3. PCIe Read: NIC отправляет электрический сигнал по шине PCIe (TLP Read Request). Контроллер памяти (MMU) возвращает 16 байт дескриптора.
  4. Extraction: NIC извлекает из дескриптора 64-битный адрес буфера данных (например, 0xFF1000).
  5. Write Packet: NIC начинает пересылать байты принятого пакета (Payload) прямиком по адресу 0xFF1000. CPU в этот момент может спать или считать числа Фибоначчи — он не задействован.
  6. Write Back: Закончив, NIC снова пишет в RAM (в дескриптор), выставляя бит статуса DD=1 (Descriptor Done).

Kernel Memory & sk_buff

Linux не копирует пакеты. Это правило №1. Вместо этого мы передаем указатель на огромную структуру sk_buff.

2.1. Ассемблерная Реальность

Как добавить заголовок к пакету, не двигая байты? Функция skb_push. 

void *skb_push(struct sk_buff *skb, unsigned int p_len) {
    skb->data -= p_len;
    skb->len  += p_len;
    return skb->data;
}

На уровне регистров процессора (x86-64) эта операция выглядит так:

MACHINE CODE EXECUTION

  • MOV RAX, [RDI + 0xD0] — Процессор загружает текущее значение указателя data из памяти (по смещению 0xD0 от начала структуры) в регистр аккумулятора.
  • SUB RAX, RSI — Вычитает длину заголовка из адреса. Адрес сдвигается "влево" (в сторону младших адресов).
  • MOV [RDI + 0xD0], RAX — Сохраняет новый адрес обратно в память.
  • Теперь, когда код будет писать по skb->data, он будет писать в свободное пространство ПЕРЕД старыми данными. Стоимость: 3 такта.

Namespaces

В ядре нет структуры "Контейнер". Есть только struct nsproxy.

Когда процесс делает socket(AF_INET, ...), ядро неявно использует указатель current->nsproxy->net_ns, чтобы найти нужную таблицу маршрутизации. Именно поэтому процесс в "контейнере" не видит интерфейс eth0 хоста — его дерево объектов просто не содержит ссылки на него.

Virtual Switching (Veth & Bridge)

Veth — это не труба. Это залинкованные структуры.

The DNS Recursive Resolver

Прежде чем отправить первый TCP SYN пакет, приложение должно узнать IP-адрес. Это задача DNS Resolver. В Linux это не магия ядра, это обычная библиотека (glibc), работающая в User Space.

5.1. System Call: getaddrinfo

Когда ваш код вызывает getaddrinfo("google.com", ...), происходят следующие события:

  1. Config Parsing: Glibc открывает /etc/resolv.conf. В Docker-контейнере там обычно написано nameserver 127.0.0.11.
  2. Socket Creation: Glibc создает UDP сокет (socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP)).
  3. Packet Construction: Библиотека вручную собирает DNS-пакет в буфере памяти.

BINARY FORENSICS: THE DNS QUERY PACKET

DNS пакет — это структура из хедеров и секций. Взглянем на байты запроса для google.com.

1. Header (12 Bytes) 
Transaction ID: 0x1a2b  (Random matching ID)
Flags:          0x0100  (Standard Query, Recursion Desired)
Questions:      0x0001
Answer RRs:     0x0000
Authority RRs:  0x0000
Additional RRs: 0x0000
2. Question Section (Encoding)

DNS использует формат "Length-Value" для частей домена (Labels). Точки не передаются.

0x06 'g' 'o' 'o' 'g' 'l' 'e'  (Length 6, "google")
0x03 'c' 'o' 'm'              (Length 3, "com")
0x00                          (Null Terminator, End of Name)
0x00 0x01                     (Type: A Record)
0x00 0x01                     (Class: IN)

5.2. UDP Transport & Recursion

Glibc вызывает sendto(), отправляя эти ~30 байт на 127.0.0.11:53. Почему UDP? Потому что Handshake TCP удвоил бы время задержки.

Если локальный резолвер не знает ответа, он начинает рекурсию:

  1. Спрашивает Root Server (один из 13 мировых IP, например 198.41.0.4). "Кто отвечает за .com?"
  2. Root отвечает: "Я не знаю IP гугла, но знаю, что за .com отвечают сервера Verisign".
  3. Резолвер спрашивает сервер Verisign. Тот посылает на ns1.google.com.
  4. Наконец, ns1.google.com отдает заветный IP.

TCP: The Connection

Получив IP, мы начинаем TCP Handshake.

STATE MACHINE: 3-WAY HANDSHAKE

  1. SYN: Клиент выбирает случайное число $Seq = X$. (State: SYN_SENT).
  2. SYN-ACK: Сервер выбирает $Seq = Y$, подтверждает $Ack = X+1$. (State: SYN_RECV).
  3. ACK: Клиент подтверждает $Ack = Y+1$. (State: ESTABLISHED).

Только теперь ядро создает структуру struct sock в состоянии ESTABLISHED и готово передавать данные.

Cryptography & TLS 1.3

Самая математически насыщенная часть. Как передать секрет по открытому каналу?

7.1. Elliptic Curve Diffie-Hellman (ECDH)

В TLS 1.3 мы используем кривую Curve25519. Ее уравнение:

$$y^2 = x^3 + 486662x^2 + x \pmod {2^{255}-19}$$

DERIVATION: THE SHARED SECRET

Пусть $G$ — базовая точка кривой (генератор).

  1. Client: Генерирует секретное число $a$ (private key).
    Вычисляет публичный ключ $A = a \times G$. (Умножение точки на скаляр).
    Отправляет $A$ серверу в сообщении ClientHello.
  2. Server: Генерирует секретное число $b$.
    Вычисляет $B = b \times G$.
    Отправляет $B$ клиенту в ServerHello.
  3. Magic:
    Клиент вычисляет $S = a \times B = a \times (b \times G)$.
    Сервер вычисляет $S = b \times A = b \times (a \times G)$.

Поскольку умножение на скаляр коммутативно ($a \cdot b = b \cdot a$), они получают одинаковую точку $S$. Координата $x$ этой точки становится общим секретным ключом (Pre-Master Secret).

7.2. Galois Field Arithmetic (AES-GCM)

Шифрование — это не проблема. Проблема — это аутентификация (убедиться, что данные не подменили). Для этого используется GCM (Galois Counter Mode), работающий в поле Галуа $GF(2^{128})$.

Полином поля: $$P(x) = x^{128} + x^7 + x^2 + x + 1$$

Операция умножения в этом поле ($A \otimes B$) сложна для обычного CPU. Поэтому Intel добавил инструкцию PCLMULQDQ (Carry-less Multiplication), которая выполняет полиномиальное умножение аппаратно. Это позволяет шифровать и подписывать трафик на скоростях 10-100 Гбит/с.

7.3. X.509 Certificates & Chain of Trust

Как браузер узнает, что ключ $B$, присланный сервером, действительно принадлежит rudolf-music.ru, а не хакеру посередине? Ответ: Цифровая Подпись.

NUCLEOLAR LEVEL: ASN.1 STRUCTURE

Сертификат — это структура Certificate, описанная на языке ASN.1. 

Certificate  ::=  SEQUENCE  {
    tbsCertificate       TBSCertificate,  -- "To Be Signed" (Body)
    signatureAlgorithm   AlgorithmIdentifier,
    signatureValue       BIT STRING       -- The Encrypted Hash
}

TBSCertificate  ::=  SEQUENCE  {
    version         [0]  EXPLICIT Version DEFAULT v1,
    serialNumber         CertificateSerialNumber,
    signature            AlgorithmIdentifier,
    issuer               Name,            -- Who signed this? (R3)
    validity             Validity,        -- NotBefore / NotAfter
    subject              Name,            -- Who owns this? (rudolf-music.ru)
    subjectPublicKeyInfo SubjectPublicKeyInfo, -- THE PUBLIC KEY ITSELF
    extensions      [3]  EXPLICIT Extensions OPTIONAL
}

Самое важное поле — subjectPublicKeyInfo. Именно тут лежит публичный ключ сервера ($e, n$ для RSA или точка $P$ для ECC), который мы используем для обмена ключами.

MATHEMATICAL PROOF: A CONCRETE EXAMPLE

Перестанем говорить абстракциями. Давайте "взломаем" RSA на калькуляторе. Представим, что мы — CA (Certificate Authority), и подписываем хеш сертификата.

1. Генерация ключей CA (Keygen)
Взяли два простых числа: $p = 61, q = 53$.
Модуль $n = p \times q = 3233$.
Функция Эйлера $\phi(n) = (61-1)(53-1) = 3120$.
Выбрали открытую экспоненту $e = 17$ (должна быть взаимно проста с $\phi(n)$).
Вычислили секретную экспоненту $d = 2753$ (обратное к $e$ по модулю $\phi(n)$).
Public Key: $(17, 3233)$, Secret Key: $(2753, 3233)$.
2. Подписание (Signing)
Пусть хеш сертификата $H = 65$. (В реальности это 32 байта SHA-256).
CA вычисляет подпись $S$, используя свой SECRET KEY $d$:
$$S = H^d \pmod n = 65^{2753} \pmod{3233} = 2790$$
Число 2790 записывается в поле signatureValue сертификата.
3. Верификация (Verification)
Браузер получает сертификат, видит подпись $S = 2790$.
Браузер знает PUBLIC KEY CA ($e=17, n=3233$) — он зашит в ОС.
Браузер вычисляет:
$$H_{check} = S^e \pmod n = 2790^{17} \pmod{3233}$$
Если посчитать (через Modular Exponentiation), результат будет 65.
$$65 == 65$$
Магия работает. Никто, не зная $d=2753$, не мог бы подобрать такое число $S=2790$, которое при возведении в 17-ю степень даст 65.

The Browser Engine

V8 — это не интерпретатор. Это JIT-компилятор.

8.1. Inline Caching

V8 запоминает смещения полей в объектах (Shapes). Вместо того чтобы каждый раз искать "где лежит поле x" в хеш-таблице, V8 переписывает сам себя, вставляя инструкцию прямого доступа к памяти. 

// Before Optimization
CALL HashLookup("x")
MOV EAX, [Result]

// After Optimization (Hot Path)
CMP [ObjectMap], ExpectedShape  ; Check strictly
JNE Deoptimize
MOV EAX, [RCX + 16]             ; Direct Access!
